# RFab Viewer — "the one-row button minimizes the app" and the blank taskbar icon (2026-10-30)

Reported by Collins while reviewing comic pages in grid view: clicking "the line that is meant
to force everything onto one line" minimized the window instead, it seemed to depend on how
many pictures were in the grid, and the app's button in the taskbar had no icon.

Diagnosed from `%TEMP%\rfab_viewer.log`, the live windows of the running
`dist\RFab Viewer.exe` (pid 25112, enumerated with Win32), the sources PyInstaller had packed
into that exe (`%TEMP%\_MEI265882\peek`, identical to the repo apart from line endings), and a
reproduction run from source against the same eight pages.

## 1. The minimize

**The one-row button cannot minimize the window.** `_set_layout_1row` sets the mode and calls
`_do_layout()`, which only moves cells. A test from source with the same eight 1800x3819 pages,
in a normal window and in full screen, clicking the one-row / two-row / auto buttons both with
synthesized Qt clicks and with real mouse input (`SendInput` on the floating bar), never changed
the window state; the log of the session shows every layout click landing (`_do_layout` at the
unchanged window size) with the window still there afterwards.

**What the bar looked like.** The grid's bar, left to right, was
`≡ ━ ═ ⌂ ♪ — ⛶ ✕`: three layout buttons, then the window controls. The one-row button was
U+2501 (a heavy horizontal line) and the minimize button was an em dash. At 14 px, in a 28 px
button, they are the same picture: a short white line. Snapshot of the bar before the change,
rendered by Qt itself:

    [≡] [—] [=] [⌂]  [—] [⛶]

Two line buttons on one bar, one of which minimizes the window, with no tooltip on the
minimize button. Which one gets hit depends on where the hand goes, which is why it looked
count-dependent: the layout buttons sit at the left end of the bar and the controls at the
right, and the bar is 272 px wide on a 3440 px monitor (and the same 272 *physical* px on the
4K monitor, where Qt's DPI scaling is off, so the whole bar is tiny).

**Fix** (`peek/resizable.py`, `peek/grid_view.py`):

- The layout buttons are drawn icons now, not font glyphs: little boxes, 2x2 for auto, **1x3 for
  "everything in one row"**, 2x3 for two rows. The minimize button is the classic short bar at
  the bottom of the button. Nothing on the bar is a plain horizontal line any more.
- A 14 px gap separates the layout group from the window controls (`bar_width()` is now the one
  formula for the bar's width; the grid's "hide the cell X under the bar" code uses it too).
- Every bar button has a tooltip: Auto grid / Everything in one row / Two rows / Home /
  Mute / Minimize / Full screen (F, or double-click) / Close (Esc).
- Every bar click is logged **before** its handler runs (`BTN: minimize`, `BTN: layout 1row`,
  `BTN: fullscreen`, ...), plus `LAYOUT: one row, 8 cells`, `FULLSCREEN: on|off` and
  `MINIMIZE: window minimized by its bar button`. The old log could not say which button was
  pressed; the next report of this kind is answered by
  `grep -n -E "BTN:|LAYOUT:|FULLSCREEN:|MINIMIZE:" "%TEMP%\rfab_viewer.log"`.

## 2. The taskbar icon

Every window of the running exe had **no icon at all** (`WM_GETICON` big/small and the class
icon all 0), so the taskbar drew the generic one. Two things combined:

- `peek/main.py` loaded `peek.ico` from next to the package or from `sys._MEIPASS`, but the exe
  was built without `--add-data "peek.ico;."`: the packed bundle has `peek/` and no `peek.ico`,
  so `setWindowIcon` never ran. (The exe's own resource icon is fine: Explorer shows it.)
- Qt's Windows window class takes its icon from an exe resource named `IDI_ICON1`; PyInstaller
  stores the icon under numeric id 1, so Qt never finds it and leaves the class icon empty. The
  exe's icon therefore never reached the windows by itself either.

**Fix:** `_app_icon()` in `peek/main.py` looks beside the package, in the bundle, and beside the
exe, and in a frozen Windows build falls back to the icon Explorer shows for the exe itself
(`QFileIconProvider`), so a window is never iconless again; the log says where it came from
(`ICON: file ...` / `ICON: exe resource ...` / a warning). `build.bat` now bundles `peek.ico`
and sets the exe icon. Verified on the rebuilt exe: `WM_GETICON` returns a handle on the viewer
windows and the taskbar button shows the RFab Viewer icon.

**macOS is the exception, on purpose.** In the `.app` the function returns a null icon and
nothing calls `setWindowIcon`: the bundle's `peek.icns` is what the Dock shows, and on macOS
`QGuiApplication.setWindowIcon` REPLACES the Dock icon (Qt's Cocoa integration hands it to
`NSApp.applicationIconImage`). The first cut of this fix, shipped to S3 by the Mac workflow at
12:20 on Oct 30, would have put the generic executable icon in the Dock for the whole run
(the Mac bundle has no `peek.ico`, so the exe-icon fallback fired). Caught on review the same
afternoon; the dmg was rebuilt from the corrected commit. The log line there is
`ICON: app bundle (macOS), left to the bundle`.

## Rebuilding

`build.bat` is the whole build (there is no committed `.spec`; `*.spec` is git-ignored, which is
why the one FIXES_2026-09-29.md mentions did not exist on this machine):

    python -m PyInstaller --noconfirm --clean --onefile --windowed --name "RFab Viewer"
        --icon peek.ico --add-data "peek.ico;." --add-data "peek;peek" main.py

It needs `pip install PySide6 Pillow pyinstaller` once (done on the desktop Oct 30 2026 with
`--user` into the Program Files Python 3.13; PySide6 6.12.0, PyInstaller 6.22.3). The output
replaces `dist\RFab Viewer.exe` even while an old copy is running: the running exe is renamed
to `dist\RFab Viewer.prev.exe` (Windows allows renaming a running image, not overwriting it).
**Close every open viewer window once after a rebuild**: a running old instance is the
single-instance owner and receives the files of every new launch until it exits.

## 3. What rfab.ai hands out, and how each file gets there

Collins, after the fix: "did you rebuild the mac linux and windows version and make sure they
are what download from rfab". The `/downloads` page links three S3 objects straight from the
browser (`https://rfab-media.s3.us-east-1.amazonaws.com/downloads/<name>`); the backend's
`/api/downloads/rfab-viewer.*` routes redirect to the same keys. What was found on Oct 30:

| File | Was | Built by, from now on |
|---|---|---|
| `RFab Viewer.dmg` | rebuilt by the push of the fix (GitHub Actions in this repo, run 22, 12:20 EDT), with the Dock-icon problem above | `.github/workflows/build.yml` job `build-mac`, every push to master: PyInstaller, Developer ID signing, notarization, upload |
| `RFab Viewer.exe` | the Aug 20 2026 build (64,555,664 bytes), signed by hand with `trusted-signing/sign-and-ship.sh`; nothing rebuilt it since, so the site handed out the bug for ten more weeks of commits | `TheCollinsFamily/rf-bridge` `.github/workflows/build-viewer-win.yml`: that repo holds the Azure Trusted Signing secrets (this one has none, and this machine has no signing keys). Put the commit of this repo to ship in `rf-bridge/.github/viewer-release.txt` and push; the job builds the exe with the `build.bat` command, smoke-tests it offscreen, signs it, verifies `Status: Valid`, and uploads to `RFab Viewer.exe` and the legacy `rfab-viewer.exe`. Missing secrets fail the job: an unsigned exe never replaces the signed one |
| `RFab Viewer Linux.tar.gz` | did not exist. The site guide had said "Windows, Mac & Linux" for the viewer since Sep 5 2026 | `build.yml` job `build-linux` (ubuntu-22.04 so the binary runs on 22.04 and newer): PyInstaller onefile, an offscreen smoke test, then a tarball of the binary + `linux/install.sh` (menu entry, Open With, `~/.local/bin/rfab-viewer`) + `linux/README.txt`. The card on `/downloads` and the backend route `rfab-viewer-linux.tar.gz` were added the same day (FE + BE deploy owed) |

Every upload also writes `downloads/versions/<file>.json` (`commit`, `builtAt`), so "which build is
live" is one `curl` away. The Windows and Linux builds pin `PySide6==6.12.0` and
`pyinstaller==6.22.3`, the pair the local exe was tested with.

`build.bat` here still builds only the local `dist\RFab Viewer.exe` that this PC's image clicks
open; it is not a release step.

**Verified the same evening from the S3 objects themselves** (the builds of commit `3b0f068`;
a later push rebuilds all three and `downloads/versions/*.json` names whatever is live):

- `RFab Viewer.exe`, 67,127,064 bytes: Authenticode `Valid`, signer "The Pragmatist Foundation",
  Microsoft timestamp; run here on two pages, both windows carry icon handles, the log says
  `ICON: file ...\peek.ico`, the bundle holds the new sources, clean `EXIT ... code=0`. The legacy
  `rfab-viewer.exe` key was uploaded alongside.
- `RFab Viewer.dmg`, 51,339,783 bytes: `Info.plist` names `peek.icns` (present, 270 KB),
  `_CodeSignature` present, the bundled `peek/main.py` has the macOS rule above.
- `RFab Viewer Linux.tar.gz`, 99,719,069 bytes: unpacked and run (offscreen) in bare Ubuntu 22.04
  and 24.04 containers with only the Qt runtime libraries installed: `ICON: file /tmp/_MEI.../peek.ico`,
  no exception; `install.sh` placed the binary, command, icon and a valid desktop file, and
  `uninstall.sh` removed them.
